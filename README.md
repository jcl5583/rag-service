# RAG Service

一个基于 FastAPI 的文档问答服务：把资料交给大模型，让它只根据资料回答；资料里没有的，就说"没有"。

## 快速开始

```bash
pip install -r requirements.txt
cp .env.example .env      # Windows: copy .env.example .env
# 编辑 .env，填入你的 key 和 TOP_K
uvicorn app.main:app --reload
```

打开 http://127.0.0.1:8000/docs ，在 `/chat` 里提问。

## 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/health` | 健康检查 |
| POST | `/chat` | body: `{"question": "..."}` → `{"answer": "...", "sources": [...], "context_chars": 1890}` |

`sources` 返回本次回答引用到的文档名，`context_chars` 是送进 prompt 的上下文长度，用于观察成本。

## 检索方案

当前采用 **BM25 关键词检索**（中文按字符二元组切分），取 top-5 作为上下文。
### 检索方式对比（关键发现）

| 测试集 | BM25 | 向量 | 混合（RRF） |
|---|---|---|---|
| 原 20 题（问法接近原文） | 100% | 100% | 100% |
| 难 10 题（用户真实问法） | 40% | 70% | 80% |

同一套系统，换个测试集，结论完全反转。

- **BM25**：语义近似时直接召不回——字面零重合导致分数为 0，被过滤后返回空，模型只能答"资料中没有"
- **向量检索**：能处理换说法，但对精确的条款编号、数字不敏感
- **RRF 混合**：只融合两路的排名（1/(60+rank)），不看分数（量纲不同无法相加）。两路都靠前的块得双份分

**教训**：照抄原文出的测试集会严重高估检索效果。评测集本身需要设计——必须有"换说法"的题，否则测不出方法差异。

### 演进过程

| 方案 | 上下文长度 | 单次输入 token（估算） | 通过率 |
|---|---|---|---|
| 全量注入（19 块全塞进 prompt） | 6462 字 | ≈ 3900 | 4/4 |
| BM25 检索 top-3 | 1122 字 | ≈ 670 | 19/20 |
| **BM25 检索 top-5（当前）** | **1890 字** | **≈ 1130** | **20/20** |

上下文相比全量注入减少约 71%，同时测试集从 4 条扩到 20 条并全部通过。

### 第一版为什么失败

最初用「命中二元组的次数总和」当分数，结果「办法什么时候施行」「发现违法内容怎么处理」两题都回答"资料中没有提到"：

- **常见词霸榜**：标识、办法、提供者 在全文出现数十次，把真正有区分度的词（施行、罚）压下去了
- **长块占优**：装了两三条法条的块字数多，词频天然高
- **词频线性累加**：一个词出现 10 次就吃 10 倍分，不合理

换成 BM25 后解决这三个问题：IDF（稀有词加权）+ 长度归一化（b=0.75）+ TF 饱和（k1=1.5）。

### top_k 选择

| top_k | 通过率 | 平均上下文 |
|---|---|---|
| 3 | 95%（19/20） | 1122 字 |
| 5 | 100%（20/20） | 1890 字 |
| 8 | 100%（20/20） | 2984 字 |

top_k=5 是拐点：继续增大只增加上下文长度与成本，不提升准确率，因此定为默认值。

### 已知局限

BM25 只认字面重合，抓不到语义近似——同一道题换个问法（"标识办法什么时候施行" vs "生成式人工智能服务管理暂行办法什么时候施行"），一道过一道不过。
下一步接 embedding 做向量检索，与 BM25 组成混合检索。

## 评测

`eval/golden.jsonl` 共 20 条：15 条可回答 + 5 条资料中不存在（专测拒答）。
判定方式：可答题需命中期望关键词；拒答题需包含拒答表述，防止模型用编造答案刷高分。

每次改动检索、prompt 或切分后运行：

```bash
python eval/run_eval.py
```

输出通过率与平均上下文长度，用于回归对比。

## 技术栈

- Python 3.12 / FastAPI / Pydantic（自动校验 + 自动 API 文档）
- OpenAI Python SDK（指向 DeepSeek，兼容协议）
- python-dotenv（密钥不写进代码）
- 依赖版本锁定，避免 SDK 大版本升级导致接口不兼容
- embedding：BAAI/bge-m3（硅基流动，OpenAI 兼容接口）
- 混合检索：BM25 + 向量，RRF 融合

## 踩过的坑

1. `python -m venv` 创建虚拟环境失败（ensurepip 报错），改用 PyCharm 自建环境解决。
2. `requirements.txt` 拼写错误（`uvivorn`、`python-dotenvs`）导致 `pip install -r` 直接失败。
3. `.env` 变量名写成 `LLM_APT_KEY`，读不到 key——排查时应先打印变量名，而不是怀疑代码。
4. 中文乱码：同一文件用不同编码读取，显示结果不同；但**用 PowerShell 的 `Get-Content` / `Add-Content` 改写文本文件会真的把中文写坏**（默认按 GBK 解码）。换文件用 `Copy-Item` 按字节复制，或改用 Python 显式指定 `encoding="utf-8"`。
5. 真实文档的标题重复、段落粘连——后续需要加清洗步骤。
6. 用相对路径 `Path("data/docs")` 读文件，换个目录运行就读不到（返回 0 个文档）——改用 `Path(__file__).resolve().parent` 作为基准，并在目录不存在时抛错而不是静默返回空列表。
7. 调试脚本自己重写了一遍打分逻辑，测的还是旧算法——调试必须调用和生产相同的代码路径，否则测的不是同一个东西。
